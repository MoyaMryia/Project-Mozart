# 保留连续性的延迟优化

日期：2026-10-08。线程参数补丁：`c8b3ef2`。

可以继续减少计算和传输开销，同时保留文本、播放顺序和音频片段。
当前实测只找到小幅线程配置收益，尚未找到可靠的 GPU 加速方案。
较大的改动方向为模型内部流式解码，以及生成状态常驻 GPU。
这些方向仍需实现和验证，不能提前承诺延迟降幅。

## 已确认的边界

播报服务已经用不同线程生成和播放音频。继续增加同样的并行结构不会自动消除积压。
历史 CPU int8 回放中，28 个句内片段交界的时间间隙中位数为 1.50 ms，最大值为 3.46 ms。
这些值来自按音频时长等待的 ALSA `null`，不包含实体输出设备的启动或缓冲耗时。
GPU float32 回放中，相同定义的最大间隙为 571 ms，28 个交界中有 4 个超过 20 ms。

保留全部文本和正常播放速度时，输出音频总时长决定消费速度。
例如，每 10 s 输入持续产生 12 s 播报，即使合成不耗时，等待也会每轮增加 2 s。
因此，计算优化可以减少启动和断供等待，但不能保证任意输入下的延迟始终有界。
不能用扩大队列证明延迟降低，也不能把丢句后的成功样本延迟当作整体改善。

## 本轮固定文本实验

设备、模型和参考 WAV 见 [GPU 报告](GPU.md)。本轮图形服务保持运行。
各配置顺序运行相同 8 条文本，共两轮，每种配置完成 16／16 个任务。
下表只统计第二轮的 8 个任务。计时从工作进程开始处理任务至 WAV 写入完成。
生成步数为 5，随机种子为 42；五步合并实验仍执行五次数值积分。

| 配置 | 合成耗时中位数 | 说明 |
| --- | --- | --- |
| CPU int8，1 线程 | 2.310 s | 慢于原配置 |
| CPU int8，2 线程 | 1.778 s | 本轮控制组 |
| CPU int8，3 线程 | 1.637 s | 约减少 7.9%，但部分输出时长改变 |
| CPU int8，4 线程 | 1.682 s | 约减少 5.4%，输出更接近控制组 |
| CUDA float32，原流模型 | 2.454 s | CPU 线程数为 2 |
| CUDA float32，五步合并 | 2.524 s | 本轮未获得收益 |

这些数字来自单轮顺序对照，不能证明小幅差异可长期稳定复现。

### 五步合并

[Pocket 原实现](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.6/sherpa-onnx/csrc/offline-tts-pocket-impl.h)
在每个潜在帧中调用流模型五次，并在 CPU 上更新积分状态。
实验将五步展开到一个 ONNX 图中，共用原权重，并保留原时间值和步数。
外层调用一次，接收累计变化量；原工作进程和资产不变。
实验脚本为 [unroll_pocket_flow.py](../../rvc-golden/realtime-patches-20261008/unroll_pocket_flow.py)。

CPU 数值对照覆盖批大小 1、2，三种输入尺度和两次随机输入，共 12 组。
全部通过 `rtol=1e-4`、`atol=1e-5` 检查。
但完整 CUDA 音频没有获得提速，且并非逐字节等同于原模型输出。
因此，本轮不将该模型接入产品路径。
合成张量对照通过，也不能替代完整音频和延迟验证。

### CPU 线程数

3 线程的 16 份 WAV 中，12 份时长与 2 线程一致，4 份改变。
这些差异不能直接证明漏词，但需要进一步核对，不能只根据最快中位数选择该配置。
4 线程的 16 份 WAV 时长均与 2 线程一致。
其中 14 份逐字节相同，另外两份的最大样本差为一个 int16 量化单位。
4 线程全部样本的最小波形余弦相似度大于 0.99999999999。
本轮没有人工听检。

监督程序新增 `--tts-threads`。该参数只改变播报工作进程，不改变翻译线程数。
默认仍为 2。参数传递、默认值、环境隔离和非法值拒绝通过了 5 项相关回归测试。
固定文本脚本新增 `--threads`，支持独立对照。

## 完整回放

`threads3-v1` 和 `threads4-v1` 均使用提交 `c8b3ef2`。设备端 Python 工具摘要与该提交一致。
输入仍为保留的 120 s 预处理音频，翻译仍为 Qwen 0.8B Q4_K_M，RVC 关闭。
原生二进制、参考音色和播放配置保持原值。ALSA `null` 按音频时长等待。
每种配置只运行一遍；历史控制组为 `limit128-v1`。

| --- | --- | --- | --- |
| 首片合成中位数／最大值，成功 20 句 | 1.785／3.843 s | 1.601／3.695 s | 1.693／3.938 s |
| 最终识别发出至首播，中位数／最大值 | 10.479／24.094 s | 9.444／20.260 s | 10.520／19.999 s |
| 播报提交至首播，中位数／最大值 | 9.934／23.768 s | 8.844／19.878 s | 9.930／19.634 s |
| 完成播报数／最终识别句数 | 20／23 | 20／23 | 20／23 |
| 已准入播报完成数／准入数 | 20／20 | 20／20 | 20／20 |
| 句内交界间隙中位数／最大值，共 28 个 | 1.50／3.46 ms | 1.50／4.94 ms | 1.60／7.96 ms |

两种新配置的 23 条最终源文本和 21 条成功译文均与控制组相同。
两条翻译检查失败仍保留。控制组拒绝第 21 句播报，新配置均拒绝第 19 句。
因此，覆盖率没有增加，也没有减少；获准播报的集合改变了。
不能把两组首播中位数差当作每句都获得的收益。

4 线程与控制组共同完成 19 句。17 份完整 WAV 的 PCM 逐字节相同。
另外两份时长相同，最大样本差为一个 int16 量化单位。
共同句的提交至首播耗时，逐句差值中位数为增加 60 ms，平均值为减少 465 ms。
这一轮不支持整体首播明显提速，但支持首片合成略快且片段衔接未出现明显退步。
3 线程的共同 19 句中，只有 13 份音频时长与控制组一致；本轮不推荐它作为默认配置。

两轮均完成 6,000 帧采集，输入溢出为零，字幕修订和播放顺序正确。
全部 20 份已完成 WAV 均与各自片段按序连接的 PCM 一致，int16 满幅样本数为零。
两轮句内间隙超过 20 ms 的数量均为零。
最低可用内存分别为 4.306 GiB 和 4.307 GiB。
测试程序均以状态码 0 退出，本轮子进程和服务端口已清理，图形服务保持运行。

可通过以下参数选用保守候选，通用启动器的默认值仍为 2：

```text
--tts-provider cpu --tts-precision int8 --tts-threads 4
```

此配置可减少部分合成时间，但不能承诺降低完整首播延迟。
汇总与逐项对照见 [continuity-results.json](continuity-results.json)。

## 后续实现顺序

### 提前解码并传出音频

当前 Pocket 先生成完整句段的潜在序列，再分块解码。
Python 工作进程又等 `generate()` 返回后才写出 WAV，播报服务随后才能播放。
因此，仅把 Python 回调分得更小，不能消除前面的完整潜在序列等待。

下一步可让原生实现按现有解码块大小提前解码，并保留解码器状态。
工作进程再通过增量协议向播报服务传出 PCM（脉冲编码调制）音频块。
该方案应保留文本、五步生成和片段顺序，并让后续计算与前段播放重叠。
它需要同时修改原生实现和工作进程协议，尚未实现。
提前播放后不能撤回已播出的音频；实现必须明确处理迟发生成错误和取消。

### 让生成状态常驻 GPU

[Pocket 模型实现](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.6/sherpa-onnx/csrc/offline-tts-pocket-model.cc)
通过普通会话调用接收并转交语言模型状态与解码器状态。
[ONNX Runtime 的 I/O Binding](https://onnxruntime.ai/docs/performance/tune-performance/iobinding.html)
允许将输出保留在目标设备，减少默认输出回到 CPU 后再次上传的工作。
应先覆盖状态张量、流模型输入和积分更新，再考虑减少内核启动开销。

CUDA Graph 也不是当前可直接启用的加速开关。
[官方约束](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html#using-cuda-graphs)
要求图节点全部分配到 CUDA，且同一捕获的输入输出形状与地址保持不变。
当前记录仍有 CPU 执行层节点，不满足直接套用的前提。

上述改动验收时，应同时比较首播延迟、全部任务完成率、句内间隙、音频时长和输出差异。
不能只比较首个回调，也不能仅凭执行层列表认定优化有效。
