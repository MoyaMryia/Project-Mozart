# 首播延迟拆分与翻译长尾短测

日期：2026-10-08。基线为 [上一轮板测](RESULTS.md) 的 `base-v1` 和 `refine-v1`。
首播延迟主要来自等待。加速合成不能消除顺序播放的积压。
本轮采用一个独立小补丁：`8e610e0` 将翻译输出上限从 300 降到 128 token。
提示词、文本检查和一次重试保持不变。
新回放削减了翻译长尾，但最长首播延迟没有改善。

## 既有首播延迟的拆分

下表只统计已完成播报的 20 个任务。起点为播报服务接收任务，不含识别和翻译。
各项采用平均值，因此同一列的三个阶段可以相加。
合成前排队包含等待之前任务生成，以及延迟准入等待。
首片就绪前的时间包含计算、进程通信和音频缓冲预算等待。

| 阶段 | 不启用复核 | 启用后台复核 |
| --- | --- | --- |
| 接收任务至开始处理 | 6.141 s | 6.139 s |
| 开始处理至首片就绪 | 1.920 s | 1.904 s |
| 首片就绪至开始播放 | 4.489 s | 4.486 s |
| 合计 | 12.551 s | 12.528 s |

首片计算的中位数分别为 1.685 s 和 1.655 s。
不能把约 12 s 的整体等待全部当作模型计算时间。

### 零合成耗时的推算

推算固定以下数据：原有 20 个已完成任务、提交时刻、每份音频时长和播放顺序。
假设每份音频在任务提交时立即就绪，且只有一个输出设备。
下一份音频只能在上一份播放结束后开始。
这是理想下界，不是 GPU 实测，也没有模拟重新准入任务。

不启用复核时，首播等待中位数仍为 9.571 s，平均值为 10.048 s。
启用后台复核时，对应值为 9.522 s 和 10.039 s。
相对现有结果，逐任务减少量的平均值约为 2.5 s。
因此，只加速模型不能让当前整批播报稳定跟上输入。

推算脚本为 [latency_breakdown.py](../../rvc-golden/realtime-patches-20261008/latency_breakdown.py)。

## 翻译对照短测

设备和模型保持上一轮配置。测试只运行翻译，没有运行识别或播报。
输入为 `base-v1` 留存的同一批 23 条最终识别文本。
各配置顺序运行，没有随机交叉试验，因此小幅差异不能视为稳定收益。
每次模型服务加载完成后才开始请求计时。
脚本记录每个请求的耗时、token 使用量、重试输出和文本检查结果。

| 配置 | 文本检查通过 / 输入数 | 成功请求中位数 / 最大值 | 成功译文总词数 |
| --- | --- | --- | --- |
| 原提示词，300 token | 21 / 23 | 0.313 / 6.902 s | 396 |
| 原提示词，128 token | 21 / 23 | 0.315 / 3.639 s | 396 |
| 简短提示词，128 token | 21 / 23 | 0.372 / 1.007 s | 325 |

仅降低输出上限时，23 条结果的最终译文、状态和拒绝原因均与原配置一致。
最长请求仍需重试，但第一次扩写在 128 token 处结束，而不是继续到 300 token。
该句的重试结果包含 48 个输出 token；最终译文与原配置一致。
此次对照支持削减异常扩写长尾，不能证明所有长句都能在新上限内完成。
合法长译文仍可能被拒绝；原文字幕和错误记录继续保留。

简短提示词减少了约 18% 的总词数，但人工对照发现漏义。
例如，第 1 句的译文漏掉末尾问题，第 11 句漏掉前面的时间与过程描述。
第 21 句反而变长。文本检查通过不能证明语义完整或准确。
因此，本轮没有采用简短提示词。

对照脚本为 [translation_probe.py](../../rvc-golden/realtime-patches-20261008/translation_probe.py)。
原始结果位于 `rvc-golden/realtime-patches-20261008/translation-probe-v2` 和 `translation-probe-v3`。
首次脚本启动因运行库搜索路径缺失而失败，尚未加载模型。
修正测试环境后，后两轮均完成并清理本轮服务。

## 同输入回放验证

`limit128-v1` 使用提交 `8e610e0`，回放同一份 120 s 输入。
Python 工具摘要与该提交一致。原生二进制、模型、参考音色和播放配置保持上一轮设置。
下表的延迟只统计成功样本；翻译为 21 条，首播为 20 条。

| 指标 | 基线 `base-v1` | 输出上限补丁 `limit128-v1` |
| --- | --- | --- |
| 翻译计算中位数 / 最大值 | 0.351 / 6.893 s | 0.347 / 3.650 s |
| 最终识别发出至首播，中位数 / 最大值 | 13.215 / 22.917 s | 10.479 / 24.094 s |
| 播报提交至首播，中位数 / 最大值 | 12.172 / 22.565 s | 9.934 / 23.768 s |
| 完成播报 / 最终识别句数 | 20 / 23 | 20 / 23 |
| 播报被容量限制拒绝的句序号 | 19 | 21 |
| 完成播报总时长 | 118.56 s | 121.28 s |

新回放的 23 条源文本、21 条成功译文和两条翻译拒绝原因均与基线一致。
共同完成的 19 份播报 WAV 逐字节一致。
但准入时机改变了播报来源：第 19 句新获准播报，第 21 句被拒绝。
因此，两组中位数的差不能当作每句都减少了约 2.7 s。
共同播报的 19 句中，提交至首播耗时的减少量平均为 1.330 s，中位数为 0.338 s。
其中最大减少量为 3.266 s，最大增加量为 1.500 s。

新回放产生 269 次临时字幕更新。识别事件发出至 SSE 接收的中位数为 98 ms，最大值为 200 ms。
这些数字不包含语音至识别的耗时，也不包含浏览器渲染或实体扬声器延迟。
6,000 帧采集均完成，输入溢出为零。字幕修订和 48 个片段的播放顺序正确。
完整 WAV 的 PCM 与片段连接结果一致，未出现 int16 满幅样本。
最低可用内存为 4.20 GiB；交换空间使用量和换入页数为零。
监督程序以状态码 0 退出，没有本轮残留进程，相关服务端口已释放。

本轮通过了 39 项相关 Python 回归，包括截断拒绝、重试、数字检查和后台字幕派发。

## 下一步重点

播放设备必须按音频时长消费输出。GPU 合成不会缩短这些既有音频。
后续应先评估较短的播报文本、播放速度，以及尚未开始任务的过期策略。
每种策略都要同时报告延迟和覆盖率，避免只用丢弃旧句换取更低的成功样本延迟。
字幕传输的 200 ms 轮询仍可单独优化，但它不会消除数秒的播报等待。

原有三个补丁的回退说明见 [临时补丁记录](../repository-audit-20261008/TEMPORARY_PATCHES.md)。
若只回退本轮输出上限，执行 `git revert 8e610e0`。
