# 提前输出音频

日期：2026-10-09。实测实现：`91100e4`。连接：`ssh jetson-wg`。

提前输出已实现，并通过固定文本对照和两轮 120 s 回放。
同一新运行时内，提前输出没有改变完整 PCM（脉冲编码调制）音频。
本次保留全部 23 句播报，包括一条翻译检查失败的候选。
本次没有实体声卡测试或人工听检。

## 实现

原流程先生成完整文本片段的潜在帧，再解码音频。
补丁每生成 15 个潜在帧就解码一次，保留 Mimi 解码器状态。
一个完整音频块约为 1.2 s；末块可以更短。
工作进程保存音频块后立即通知播报服务。
同一逻辑播报任务的所有音频块使用一个原始 PCM 播放管道。
文本分段、生成步数 5、随机种子 42、解码块大小和输出顺序保持原设置。

功能需要独立编译的 sherpa-onnx 1.13.6，默认关闭。
构建脚本固定源代码和 ONNX Runtime 归档摘要，并验证补丁后的头文件摘要。
工作进程核对运行时清单及扩展库摘要；不满足条件时，启动失败。
下载任务仍使用完整片段输出。
取消、生成失败和播放失败均停止该任务的剩余输出，并保留明确状态。
生成错误可能发生在首块播放之后。已经送到设备的音频无法收回。

提前输出无法使用未来样本的峰值计算全片段增益。
因此，该模式使用单位增益，并将单个样本限制到 [-0.98, 0.98]。
普通输出继续使用原来的全片段增益计算。
本次全部实测样本均未触发限制；这不保证其他输入逐样本相同。
非有限样本、峰值超过 4、时长超限和未确认结束仍会使任务失败。

## 固定文本对照

设备为 Jetson Orin Nano Super。PocketTTS 使用 CPU int8、2 线程。
ONNX Runtime 为 1.27.1。模型、参考 WAV 和 8 条文本保持一致。
三组各运行两遍，每组提交 16 次，完成 16／16 次。
下表只统计第二遍的 8 次热运行。
“首音频可用”从发出合成请求计时，到测试程序收到可播放输出通知。
普通模式收到完整 WAV；提前模式收到首块 WAV。

本功能保留独立运行时和显式开关，便于继续听检及回退。

## 完整回放

两轮使用同一个独立运行时。对照轮关闭提前输出，第二轮开启提前输出。
输入为保留的 120 s 预处理 WAV；不重复运行 RNNoise。
翻译使用 Qwen 0.8B Q4_K_M；PocketTTS 使用 CPU int8、2 线程。
RVC 关闭，图形服务保持运行。
输出为按音频时长等待的 ALSA `null`。每种模式只运行一轮。

“生成到首音频可用”从该任务开始处理计时，到服务保存首个可播放块。
“最终字幕到首播”从最终识别字幕的 `asr_emitted_at` 计时，到服务开始播放。
后一个指标包含翻译、合成和播放排队时间。
这些时间不包含从说话开始到最终识别字幕产生的等待。

23／23 份完整 WAV 均等于音频块按序连接的 PCM。
音频块播放顺序正确，满幅样本数和受限样本数均为零。
103 个交界包含 74 个同一文本片段内的音频块交界，以及 29 个文本片段交界。

提前输出轮仅有 4／23 句在首个文本片段合成结束前开始播放。
21／23 句在首块就绪后仍等待超过 100 ms；首块就绪到播放开始的中位数为 3.98 s。
生成开始到首播的中位数仍为 4.90 s；最终字幕到首播仍为 10.53 s。
本补丁减少了等待完整首片段的时间，没有消除覆盖率优先队列的积压。
单轮结果不能证明长期延迟稳定性。

两轮退出状态均为 0，未完成任务和等待播报任务均为零。
存储警告和预热错误均为空，本轮子进程均已退出。

## 使用与回退

在配置好的 Jetson Python 环境中，构建独立运行时：

```bash
.venv/bin/python tools/build_pocket_early_audio.py rvc-golden/early-audio-runtime
```

为实时启动命令添加下列选项：

```text
--early-audio --tts-pythonpath /absolute/path/to/rvc-golden/early-audio-runtime/python
```

本次已构建的设备端运行时目录为：

```text
/home/moyamryia/mozart-realtime-patches-20261008/early-audio-runtime-20261009/python
```

要恢复旧安装包和完整片段输出，删除上述两个启动选项。
要在新运行时内对照，只删除 `--early-audio`。
