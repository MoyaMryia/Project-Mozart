# 实时延迟改进方案

日期：2026-10-08。依据当前代码与保存的 Jetson 测量。没有重新执行模型推理或物理音频测试。
本方案暂缓文件变声性能优化。下文区分代码确认、历史实测与待验证改法。

## 1. 先拆开字幕、翻译和播报提交

补丁前，`tools/subtitle_bridge.py` 在同一循环读取 ASR、同步翻译、同步提交播报，最后才写字幕 JSONL。
本轮小补丁改为原文先发布，译文在播报请求前发布，播报提交结果最后发布。
前端按同一 `utterance_id` 和递增 `revision` 更新原行，并显示翻译中或失败状态。
Python 88 项回归、前端字幕四项回归和生产构建通过；尚无新的 Jetson 延迟测量。
读取、翻译与播报提交仍串行执行；翻译时不能继续读取后续 ASR 结果。
`tools/stt_service.py` 的 partial 目前是终端文本，桥接进程只接收 final JSON。

建议按以下顺序改造：

1. ASR 读取任务立即发布原文事件，并把翻译工作放入有界队列。
2. 单个翻译 worker 按原序处理 final；完成后发布同一 `utterance_id` 的新 revision。
3. 前端按 ID 更新原行，拒绝旧 revision；原文、翻译中、已翻译和失败状态分别显示。
4. 播报提交使用单独有界队列；其失败、超时或容量不足不阻塞字幕发布。
5. 增加仅原文模式，跳过翻译；可选 partial 只用于可修订的显示，不触发播报或计入 final 覆盖。

过载时保留原文和明确的翻译/播报缺失状态，不静默删句。保留数量、否定和边界检查，未经检查的译文不进入 TTS。
不并行启动多个 GPU 翻译请求来假定提速。先移除读取与发布的串行等待，再测翻译服务容量。

最新短测中，18 个成功译文从 ASR final 输出至译文就绪的中位数为 2.32 s，最大 3.80 s。
以上改法可以使原文不再等待这段处理；不能据此保证完整字幕显示延迟减少相同数值。
SSE 当前每 200 ms 检查文件。事件通知或较短的等待可进一步减少发布延迟，但不是十秒级播报等待的主要来源。

离线验证：模拟慢翻译和阻塞播报提交，确认原文继续发布；检查顺序、revision、错误显示、有界容量、取消和退出。

## 2. 播报优先分析时间线，再优化首片段

最新 18 个任务中，提交至首播中位数 8.96 s，最大 26.24 s。
首片段合成中位数 2.28 s；合成前排队中位数 3.42 s，音频就绪后等播放中位数 5.29 s。
各中位数不能相加。

最慢任务的同一条时间线为：

- 提交至开始处理：16.28 s。
- 开始处理至首片段就绪：2.44 s，其中 worker 合成计时 1.54 s。
- 首片段就绪至播放启动：7.52 s。
- 提交至首播：26.24 s。四舍五入可能产生 0.01 s 差异。

这证明该任务的主要等待位于处理前和播放前，不能直接归因于模型计算。
需要用已有片段时间线区分：前句必须占用的播放时间、合成串行等待、预算等待和可避免的播放器空闲。
只有最后一项可以通过调度直接回收；保持完整内容、原序和正常语速时，前句的播放时长仍然存在。

可评估的改法：

- 首片段优先选择较早的完整从句；后续保留较长片段，避免全部碎片化增加重复初始化和生成成本。
- 依据预测的播放时刻提前准备后续音频，保持有界缓冲；目标是减少欠载和空闲，不强行扩大现有预算。
- 使用持续 PCM 播放器，减少每片段启动 `aplay` 的开销；该开销尚未独立测量，不能声称可节省数秒。

现有时长预算、延后 FIFO、预热和原生帧数上限已经修复，不重复作为新方案。
不交错播放不同句子的首片段来降低表面首播指标。输出时长超过输入可用播放时间时，需另行评估忠实精简译文或语速策略。
这些策略会影响语义或音质；本轮不默认启用。

## 3. 真正的流式 TTS 是后续候选

当前 `tools/clone_worker.py` 只在 `tts.generate()` 完成后写 WAV 和返回结果；回调仅记录计时和时长限制。
[sherpa-onnx v1.13.6 原生实现](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.6/sherpa-onnx/csrc/offline-tts-pocket-impl.h)先生成当前内部句子的全部 latent，再解码并调用音频回调。
因此只接出回调音频仍保留前面的 latent 生成等待。

保存的 18 个首片段中，首回调中位数 1.68 s；完整生成与首回调的时间差中位数 0.39 s。
0.39 s 是当前路径可重叠的已观察时间窗口，不是保证收益或整个引擎的理论上限。
若前方仍有待播音频，提前得到回调也可能不改变实际首播时刻。

更大的改造是让 latent 生成与有状态解码交替执行，或评估支持该方式的执行路径。
需要比较同噪声输出、结束条件、数值/音质、实时吞吐、取消和播放欠载；不能在缺少板测时宣称完成。
原生实现已有参考音色 embedding 缓存，不能把再次添加同类缓存当作未经测量的主要收益。

## 4. 字幕断句与实时变声

字幕先接通原文/partial 显示，再考虑减少静音门限。
此前 100 ms 切点调整和 VAD endpoint gating 没有可靠改善识别，且出现数量融合；不重复默认采用。
新的断句策略需基于用户确认的中文源文检查数量、人称、否定和领域词，记录新增等待与缺失覆盖。

实时 RVC 的已验证基线是 240 ms 输入块、约 88 ms 推理和约 320 ms 首帧输出。
缩小输入块可能减少缓冲等待，也会增加每秒调用次数并改变跨块音质。
未完成同一输入的 Golden、ONNX 和后端对照前，保留已验证模型与默认配置；先增加分段计时。

## 执行顺序与证据

先做字幕/翻译/播报提交解耦及离线回归，再用保存的时间线检查播报调度。
首片段划分、持续播放器、流式 TTS 和 RVC 块长变化均作为可回退候选，待恢复板测后逐项验证。
先确认源字幕覆盖和语义不退化，再比较延迟；报告完整输入分母、冷/热启动和单功能/组合运行。
